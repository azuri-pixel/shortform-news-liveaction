시청자의 첫 궁금증이 설명을 따라 이해로 이어지고, 결말에서 의미가 남도록 내용을 선택하고 이야기 전체를 설계해줘. 한 제작자가 원고·자료·생성·합성·편집·음향을 함께 판단해. 장면 수·순서·구도·구현 수단과 필요한 수정은 맡길게. 장면별 사용자 중간 승인 단계를 추가하지 말고(아래 「먼저 고르기」에서 한 번 멈추는 것만 예외) 실제 생성·TTS·렌더와 확인 가능한 수정까지 수행해줘.

나레이션의 가장 첫 문장은 기사에 근거해 관심과 다음 내용을 볼 이유를 만드는 후킹 문장으로 작성해줘. 질문·대비·의외의 사실 등 내용에 맞는 형태를 선택하고 특정 문형·문장 길이·도입 시간을 강제하지 마. 첫 문장의 핵심을 일반 말자막과 별개인 큰 중앙 부근 오버레이와 노란 밑줄로 강조해줘. 화면용 문구는 의미·조건·불확실성을 유지하며 요약할 수 있어. 작은 선행 문구나 두 단계 문구 구성을 강제하지 말고 문구 개수·분할·줄바꿈과 등장·밑줄 속도·유지·퇴장을 실제 발화와 영상에 맞춰 정해줘. 위성공해의 문장 단위나 타이밍 수치를 복제하지 마. 제작·수정 경로는 pipeline reference/hook-overlay.md를 따르고 말자막은 독립적으로 유지해줘.

마지막 CTA는 모든 편에 필수로 반영해줘. 나레이션의 마지막 문장은 정확히 "여러분은 어떻게 생각하시나요? 댓글로 의견 남겨주세요."로 끝내고, 이 말이 나오는 구간에 공통 레이어의 노란 알약 문구 "구독과 댓글 부탁드려요"를 띄워줘(closing-cta@1, 별도 장면 코드에 넣지 마). 마지막 문장 앞의 결론·여운 문장은 기사에 맞게 쓰되 이 문장을 대체하거나 바꾸지 마. 고객 요청 원문: "위성공해편 마지막 CTA가 다른 영상도 유지되게 필수 반영 부탁드립니다. 여러분은 어떻게 생각하시나요? 댓글로 의견 남겨주세요" 제작 경로는 pipeline reference/closing-cta.md를 따라줘.

기사로 내레이션 원고를 새로 쓸 때는 아래 원고 규칙을 따라줘. 사용자가 원고를 제공한 편에는 이 규칙으로 원고를 고치지 마. 고객 요청 원문(2026-11-22, 사람이 고친 원고 5편의 공통점을 분석해 제안한 규칙 다섯 문장에 대해): "규칙에 반영" — 첫 문장은 질문이나 말 걸기를 우선 검토하되, 사실 자체가 강하면 평서문도 쓴다. 수치와 표현은 기사를 기본으로 하고, 1차 자료와 다르면 원고를 바꾸지 말고 따로 보고한다. 후반부에 "여기서 중요한 한 가지"를 한 번 넣는다. 그 뒤에는 새 화제나 곁가지 전망을 더하지 않고, 짧게 맺은 뒤 고정 마무리 문장으로 간다. 어려운 용어는 정확한 이름을 쓰고 쉬운 말을 덧붙인다. — 적용할 때 "여기서 중요한 한 가지"는 공통 강조(key-callout@1)가 켜지도록 문장 첫머리에 둬줘. 기사와 1차 자료가 다른 항목은 facts.md의 불일치 항목(D)에 기사 쪽을 채택했다고 적고, 원고를 보여줄 때와 완성 보고 때 원고 블록 밖에 "기사 | 1차 자료"로 알려줘. 이 보고 때문에 제작을 멈추지는 마. 기사를 기본으로 한다는 이유로 기사에 있는 추정·전망·조건·한계와 귀속을 빼거나 기사보다 세게 단정하지 마. 고객 요청 원문(2026-11-22, 괄호로 덧붙인 용어를 음성으로 어떻게 처리할지 물은 데 대해): "자막에만 표시" — 「헤일로(후광)」, 「아페론(Apeiron)」, 「원자간력(AFM)」처럼 용어에 괄호로 덧붙인 쉬운 말·원어·약어는 사용자가 원고를 제공한 편에서도 자막에만 표시하고 소리 내어 읽지 마. 자막 원고에는 괄호까지 빠뜨리지 말고 남기고, narration.txt에서는 괄호와 그 안의 말을 뺀 뒤 substitutions.json에 자막 토큰 전체를 대응시켜줘(예: "헤일로(후광)로" → "헤일로로"). 새 원고의 괄호 병기는 앞 낱말에 붙이고 괄호 안을 띄어쓰기 없는 한 낱말로 써줘. 소리로도 들려야 하거나 여러 낱말이 필요한 설명은 괄호 없이 문장에 풀어 써줘. 「85만 달러(약 11억원)」 같은 금액·단위 환산은 용어 병기가 아니므로 이 규칙으로 빼지 마. 원고를 보여줄 때는 낭독 원고 블록을 그대로 두고, 자막에만 들어가는 병기는 블록 밖에 따로 알려줘.

제출 메시지·보고에 내레이션 원고를 보여줄 때는 narration.txt와 같은 평문으로, 문장 앞에 "1. [후킹] 청량음료에 닿은 치아…" 처럼 숫자 번호(1. 2. 3.)나 [후킹]·[강조]·[고정 마무리 문장] 같은 구간 표시, 글머리표·타임코드를 붙이지 말고, 한 줄에 한 문장씩 낭독 문장만 그대로 복사해 쓸 수 있는 블록으로 줘. 구간 설명이 필요하면 원고 블록 밖에 따로 적어줘. 원고 파일에도 줄 번호를 붙이지 마. 고객 요청 원문(2026-11-16): "기사를 숏폼으로 만들 때, 내레이션 원고에 번호를 붙이지 않도록 규칙에 넣어줄 수 있나?" "내레이션 원고를 복사해서, 회사 상사에게 보고하는데, 원고 문장 앞에 번호가 붙어서 일일이 지우고 작업을 해야 한대."

context.reference_library의 지정 레퍼런스 세트에서 정보 위계, 시선 유도와 맥락, 원인-작용-결과, 실사 합성, 발화와 움직임의 연결을 이번 기사에 맞게 적용해줘. 사례의 내용·영상·편집 코드를 새 편의 내용으로 재사용하지 말고, 이번 편에 적용할 판단을 남겨줘.

기사에 적합한 실사 영상·사진을 적극적으로 탐색해 화면의 주요 재료로 활용해줘. 특정 자료 확보에 실패하면 이야기에서 필요한 역할을 기준으로 탐색 범위와 표현을 다시 판단해줘. 영상과 이미지는 전체 화면 활용을 기본으로 하고, 기사의 핵심 원리를 설명하는 1~2장면은 입체감·움직임·단계적 변화가 있는 대표 그래픽으로 만들어줘. 납작한 선·점·막대나 멈춘 그림 위 라벨만으로 끝내지 말고 원리가 움직임 자체에서 보이게 하되, 입체 표현이 사실이나 수치 비교를 왜곡하면 정확한 쪽을 택해줘. 나머지 장면은 실사 영상·사진을 주재료로 하고 도해는 설명에 필요한 곳에 써줘. 이미지·영상·모션그래픽·생성 표현을 장면의 목적에 맞게 선택하고 결합해 미술 완성도가 이어지게 해줘. 고객 요청 원문(2026-11-11): "가능하면 앞으로도 시각적 몰입도를 높일 수 있는 영상을 찾아야 해." — 정지 사진보다 움직이는 영상 자료를 먼저 찾고, 공식 영상이 없으면 생성 영상으로 움직임을 더하는 방안을 검토해줘.

각 구간에서 시청자가 무엇을 이해해야 하는지 먼저 정하고, 핵심 대상·작용·결과가 무음으로도 어느 정도 읽히게 해줘. 강조만으로 충분한 내용과 원리·과정을 보여줘야 하는 내용을 구분해줘. 설명이 진행되면 처음 보던 대상에서 다음 대상·관계로 시선이 이어지게 하고, 같은 설명에서는 시각적 기준을 유지하되 구도·거리·가림·공간은 내용에 맞게 바꿔줘. 기존 그래픽 패턴을 관성적으로 반복하지 말고 확보한 자료와 이번 설명에 맞춰 설계해줘.

도해가 필요하면 완성된 영상 그래픽 수준으로 다듬어줘. 대상의 특징이 읽히는 형태, 주목 대상과 보조 요소의 크기·대비 위계, 여백과 정렬, 일관된 색과 선을 갖추고 관계와 변화가 그림 자체에서 이해되게 해줘. 내레이션에 맞춰 필요한 요소를 단계적으로 드러내고, 설명이 완성된 상태는 이해할 시간을 줘. 깊이감·질감·조명·카메라 움직임과 등장·퇴장·속도·easing은 설명·분위기·실제 발화에 맞게 선택해줘.

「먼저 고르기」: 고객 요청 원문(2026-11-22, 확정 5편의 1차 시안과 최종본을 비교해 제안한 4가지에 대해): "4가지 반영" — 제안 4번은 "전체 렌더 전에 핵심 장면 5초 움직이는 시안과 내레이션에 얹은 음악 3안을 보여드리고 멈춥니다"이다. 따라서 이것은 사용자가 요청한 멈춤 조건이며 CLAUDE.md·config/production-defaults.md의 "요청 원문에 멈춤 조건이 있을 때"에 해당하고, production-entry.md의 "사용자가 추가 멈춤 지점을 명시한 경우"에 해당한다. 새 편은 사용자가 원고를 제공했거나 음성 전 원고 확인을 이미 거쳤어도, 음성을 만든 뒤 첫 전체 렌더 전에 한 번 멈춰줘. 보여줄 것은 (1) 핵심 원리 1~2장면 각각 약 5초의 움직이는 mp4 — 정지 이미지로 대신하지 마. 먼저 `npm run scene:proof -- <id> --mode draft --phase motion`을 쓰고, 실패하면(2026-11-22 기준 Windows에서 import 경로 오류) 멈춤을 생략하거나 공용 스크립트를 고치지 말고 out/pilots/<id>/qa/drafts/에 그 장면만 registerRoot한 entry.tsx를 만들어(import 경로는 / 사용) `npx remotion render <entry.tsx> <컴포지션 id> <출력.mp4>`로 만들어줘. 「데스크 눈 완성도 기준」: 고객 요청 원문(2026-11-26, hani_1286549에서 영상을 직접 만들어보지 않은 기자 출신 데스크가 결과 화면만 보고 "허술하다"고 돌려준 피드백 9건과 독립 검수를 정리해 제안한 7가지에 대해, "상사의 완성도 경계를 감안해서, 기본 지침에 넣을 수 있는 게 있을까?" → "여기에만 기본 지침으로 넣어줘."). 최종 확인자는 제작 공정을 감안하지 않고 결과만 본다고 전제하고, 첫 전체 시안을 사용자에게 보여주기 전에 다음을 지켜줘. (2) 라벨·지시선: 지시선 끝점이 대상(글자·간판 포함)을 가리지 않게 하고 대상 전체를 테두리 등으로 정확히 지정해줘. 건물·기관은 간판·현판을 판독해 정식 명칭으로 적어줘. (3) 실물 밀도·비율: 칫솔모·사람·세균처럼 반복되는 대상은 실물에 가까운 밀도로, 크기가 다른 대상끼리는 실제 비율을 지켜줘. 성글거나 장난감처럼 보이면 고쳐줘. (4) 과학 동작의 정확성: 화면 속 동작은 실제 작동 방식과 맞아야 해(예: 칫솔질은 모 옆면이 아니라 모 끝으로 문지른다). 치수선이 무엇을 감싸는지로 축척을 오해하게 하지 말고, 반짝임·빛 효과가 스파크·감전으로 읽히지 않게 해줘. (5) 입체 표현: "하나의 그림에서 여러각도를 보여주면서 설명해야 할 장면이 있으면 입체적으로 보여주도록 해." 각도 전환이 필요한 설명은 평면 그림을 기울이지 말고 실제 3D(@remotion/three)와 카메라 이동으로 만들어줘. (6) 완성도 균일: 한 영상 안에서 공들인 장면 옆에 납작한 2D 도식을 남기지 말고, 결론부 개념도도 대표 그래픽과 같은 수준으로 만들어줘. 상징물은 설명 없이 뜻이 읽히는 일상 사물로 골라줘(예: '실제 사용'은 컵에 꽂힌 칫솔). (7) 사용자 제출 전 독립 검수: 첫 전체 시안을 사용자에게 보여주기 전에 shot-judge(데스크가 짚을 가능성 순으로)와 fact-check를 먼저 돌리고 의미·과학 오류를 고친 뒤 제출해줘. 고친 것과 남긴 것을 제출 메시지에 적어줘. 첫 장면 인물을 외모나 출신으로 고르는 규칙으로 바꾸지 말고, 장면마다 기사와 맞는지 판단해줘.

Higgsfield의 생성·편집 기능을 적극적으로 활용해 이해와 몰입을 높여줘. 자료만으로 전달하기 어려운 공간감·과정·비유·장면 연결은 생성과 합성을 활용하되, 고유 대상의 형태·문구·작동 특성과 사실·수치·인과관계는 보존해줘. 정확히 유지해야 할 요소는 원본이나 검증된 도해·코드 합성으로 제어하고, 생성 장면이 실제 관측이나 검증된 성능으로 오인되지 않게 해줘. 고객 요청 원문(2026-11-12, hani_1274453에서 Higgsfield 약 707크레딧 사용 후 제안한 "생성 전 예상 비용을 알리고 시안부터 만든다"에 대해): "응 기본규칙으로 넣어줘" — Higgsfield 영상 생성 전에 예상 크레딧(예: 영상 1건 약 64크레딧)을 진행 메시지로 알리고, 원하는 동작이 나올지 확신이 없는 장면은 480p 시안(draft)으로 먼저 확인한 뒤 1080p로 만들고, 실제 쓰는 길이만큼(최소 길이)만 생성하며, 비용 조회와 실제 제출을 구분해줘. 무료로 쓸 수 있는 공식 영상을 먼저 찾고 없을 때 생성해줘. 고객 요청 원문(2026-11-18, hani_954742): "0:00 출처 위치에 ai생성영상 자막이 들어있어. 이를 원래 상단에 출처 쓸 때 사용하는 폰트,크기,위치로 쓰고, 문구는 \"AI활용영상\" 으로 수정해줘. 앞으로도 실사 형태로 AI생성 영상을 만들면, 출처 위치에 \"AI활용영상\"이라고 써주도록 규칙에 반영해줘." — 실사 형태의 AI 생성 영상이 화면에 나오는 동안 상단 출처 자리에 출처 표기와 같은 서체·크기·위치·색(config/attribution-style.json의 source 값)으로 「AI 활용 영상」이라고 띄어 써줘. 고객 요청 원문(2026-11-18, hani_954742): "AIv활용v영상 이렇게 상단에 실사 형태로 AI 생성 영상을 활용할 때, 출처 자막 쓸 때 띄어쓰기하도록 해줘. 이번에도 띄어쓰기 반영해주고, 규칙에 넣어줘"

기사 본문과 필요한 1차 근거·고유 대상의 형태를 확인하고 그 범위에서 외부 검색과 자료 확보를 진행해줘. 계획·예측·가정·조건·불확실성을 이미 실현된 사실처럼 바꾸지 마. 영상 상단 고정 제목·장면명·설명이나 불필요한 제작 주석은 넣지 마. 필요한 이름·수치·단위·귀속·조건은 관련 대상·수치 곁이나 자막에 필요한 순간 붙이고, 제목·자막·주석으로 같은 설명을 겹치지 마.

이미지·영상 생성은 실제 호스트의 Higgsfield MCP generate_image/generate_video를 사용해줘. 내레이션은 Typecast를 기본으로 사용하고, Typecast를 사용할 수 없으면 Higgsfield 오디오로 대체해줘. 제공자 선택과 실제 사용한 음성·정렬·속도 조절을 제작 노트에 기록해. 실제 호출 가능한 기능을 확인하고, 실행할 수 없는 기능은 실행한 것처럼 기록하지 말고 제약을 밝혀줘. 생성은 visual-system.generation_jobs와 media.assets[].generation_job에 실제 호출·입력·출력을 연결해줘. 음성은 narration begin이 성공한 뒤 생성하고 finish로 기록해줘. 최종 조립은 `npm run produce -- run <id> render`로 narration.json → timeline → sync를 연결하고, 수정 시 낭독 원문·실제 음성·자막·화면 편집 시간을 함께 갱신해줘. 세부 절차는 체크아웃의 pipeline reference/visual-production.md와 reference/production-state.md를 따라줘.
